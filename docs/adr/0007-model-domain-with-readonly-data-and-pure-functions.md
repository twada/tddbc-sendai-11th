# 0007. ドメインモデルは読み取り専用データと純粋関数で表す

- ステータス: 承認済み
- 日付: 2026-10-24

## コンテキスト

お題は STEP ごとに仕様が段階的に公開され、先の仕様は分からない。お題の進め方でも、先の STEP を想定した作り込みはしないことになっている。仕様が変わるたびに設計を素早く直せるよう、ドメインモデルは小さく、変更しやすく保ちたい。

お題のコード例は Java 風(`new 投てき(5).点数()`)だが、クラス構成を指定するものではない。

また、スキットル番号と点数はどちらも数値で表せる。同じ `number` 型にすると、「スキットル番号が点数になる」というルールを経由せずに、番号をそのまま点数として扱えてしまう。

## 決定

- ドメインの値は読み取り専用(`readonly`)のプレーンなオブジェクトや型で表し、振る舞いは純粋関数で書く。クラスは使わない。
- スキットルは番号を持つオブジェクト `Skittle`(`{ readonly number: SkittleNumber }`)として表し、生成関数 `skittle(n)` で作る。`number` で包むことで、スキットルを数値として直接扱えないようにする。
- 点数は `type Points = number` の別名とする。足したり比べたりする量なので、ブランド型にはしない。
- 点数の計算は関数 `pointsOf(skittle: Skittle): Points` で行い、「スキットル番号 → 点数」のルールをこの関数に集める。
- 型や関数は、公開済みの仕様を満たすのに必要十分な分だけ作る。新しい仕様が公開されたら、その都度設計を見直す。

## 結果

- データと計算が分かれているので、テストが書きやすく、仕様変更時に直す範囲を見つけやすい。
- 点数への変換が `pointsOf` を通ることが型で強制され、ルールがコード上で見える。
- `Points` は `number` の別名なので、任意の数値を点数として扱うことは防げない。紛らわしさが問題になったらブランド型への変更を検討する。
