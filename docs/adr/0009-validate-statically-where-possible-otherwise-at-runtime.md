# 0009. 入力は可能な限り静的に検証し、できなければ実行時に検証する

- ステータス: 承認済み
- 日付: 2026-10-24
- [ADR 0008](0008-guarantee-skittle-number-range-by-type.md) を置き換える
- [ADR 0015](0015-distinguish-assertions-from-validation.md) で補足(型で保証した前提を、表明で実行時にも確かめる)

## コンテキスト

ADR 0008 では、スキットル番号の範囲(1〜12)を型で保証し、実行時には検証しないことにした。

STEP 01-2 で、1 回の投てきで複数のスキットルを倒せるようになった(`pointsOf(...skittles)`)。お題には「各番号のスキットルは1本ずつ」とあるので、`pointsOf(skittle(5), skittle(5))` のように同じ番号が重複した入力は現実には起こりえない。

この重複を型で防げるかを実測した。

- **型レベル計算**(引数のタプル型から重複を検出する): 番号がコンパイル時にリテラルとして分かる場合しか判定できなかった。番号が `SkittleNumber` 全体の値だと誤検出し、引数の順序を入れ替えるだけで結果が変わった。配列を展開した場合は判定できなかった。エラーメッセージも「引数の数が違う」としか表示されなかった。
- **重複を表現できないデータ表現**(番号をキーにしたオブジェクト): 重複は持てなくなるが、呼び出しが `pointsOf({ 5: true, 8: true })` という不自然な形になり、Skittle を中心にした設計(ADR 0007)を作り直す必要がある。

「実行時には検証しない」という方針のままでは、静的に防げない不正な入力に対して、もっともらしい値を返してしまう。

## 決定

- 入力の制約は、可能な限り静的に(型で)検証する。
- 静的に検証できない制約、または信頼できる静的検証が実用的でない制約は、実行時に検証する。
- 各制約の扱いは次のとおり。
  - **スキットル番号の範囲(1〜12)**: 静的に検証できるので、引き続き型(`SkittleNumber`)で保証し、実行時には検証しない。
  - **スキットルの重複**: 型レベル計算は誤検出や順序依存があり信頼できないので、型では検出しない。`pointsOf` が実行時に検証する。
- 実行時の検証に失敗したら、組み込みの `Error` を投げる。メッセージには原因となった値を含める(例: 「スキットル 5 が重複しています」)。重複が複数ある場合は、最初に見つかったものだけを報告する。
- 静的な決定は `@ts-expect-error` を付けた型レベルテストで、実行時の決定は `assert.throws` を使ったテストで残す。

## 結果

- 静的に防げる誤りはコンパイル時に、防げない誤りは実行時に検出され、不正な入力に対してもっともらしい値を返すことがなくなる。
- `pointsOf` は例外を投げうる関数になり、戻り値の型 `Points` だけでは失敗の可能性が表れない。失敗を型で表す必要が出てきたら、Result 型などの導入を新しい ADR で検討する。
- 新しい制約が出てきたら、静的に検証できるか、実用的かをまず検討し、どちらで検証するかを決める。
